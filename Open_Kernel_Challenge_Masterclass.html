Chapter 2: GPU Programming 101 — How to Think in CUDA

2.1 The Execution Hierarchy: From Threads to Grids

A GPU does not execute programs sequentially like a CPU core. Instead, it schedules thousands of tiny threads concurrently:

  • Thread: A single execution entity. It has its own private registers.
  • Warp (32 Threads): The fundamental atomic unit of execution. 32 threads execute the exact same instruction at the exact same clock cycle (SIMT: Single Instruction Multiple Threads).
  • Thread Block (up to 1,024 Threads): A group of warps assigned to a single SM. All threads in a block can communicate through Shared Memory (SRAM) and synchronize via __syncthreads().
  • Grid: The collection of all thread blocks launched by a kernel. Blocks execute independently across different SMs.

2.2 The Memory Hierarchy (The Speed Pyramid)

Understanding the memory pyramid is 90% of CUDA optimization:

Memory Level Latency Bandwidth / Scope Golden Rule
Registers 0 clock cycles Private to 1 thread Keep accumulators and loop counters here.
Shared Memory (SRAM) ~20–30 clock cycles Shared within 1 Block (228 KB/SM) Load weights or activations once; reuse many times.
L2 Cache ~200 clock cycles 50 MB shared across entire GPU Prevent cache-thrashing by sizing working tiles below 50 MB.
Global Memory (HBM3e) ~400–800 clock cycles 4.8 TB/s (141 GB) Avoid DRAM round-trips at all costs!

2.3 The Four Pillars of High-Performance CUDA

Pillar 1: Memory Coalescing

When 32 threads in a warp request memory from DRAM, the hardware memory controller does not make 32 individual requests. If thread 0 reads address 0, thread 1 reads address 1, and so on, the GPU merges them into a single 128-byte cache line transaction. If threads access scattered memory addresses, the memory controller is forced to issue 32 separate transactions, cutting memory bandwidth by 95%!

Pillar 2: 128-Bit Vectorized Loads (float4 and bfloat162)

NVIDIA GPU memory controllers operate at maximum throughput when loading 128 bits (16 bytes) in a single assembly instruction (LDG.E.128). Instead of loading one bfloat16 (2 bytes) at a time, we cast our pointers to float4 (which is 4 × 32 bits = 128 bits). A single load instruction fetches 8 bfloat16 numbers simultaneously into registers!

Pillar 3: Warp Shuffle Intrinsics (__shfl_down_sync)

Traditionally, to sum 32 numbers computed by 32 threads in a warp, developers wrote the numbers to Shared Memory and called __syncthreads(). With Warp Shuffles, threads pass register values directly to neighboring threads over dedicated high-speed silicon datapath wires in 1 clock cycle with zero memory operations.

Pillar 4: Operator Fusion

In stock PyTorch, running y = gate * norm(x) launches two separate GPU kernels:

  • Kernel 1: Reads x from DRAM, computes normalization, and writes result back to DRAM.
  • Kernel 2: Reads normalized x from DRAM, reads gate from DRAM, multiplies them, and writes back to DRAM.

Fusion combines both math steps inside GPU registers: x is read once, normalized, multiplied by gate, and written to DRAM once. This eliminates 66% of all DRAM traffic.

3.1 Vectorized 128-Bit GEMV Kernel (muse_bf16_proj)

This kernel computes y = x · WT for a single token (Batch size M = 1), accelerating the Router GEMV by 2.329× and the Unpooler GEMV by 1.777× over stock PyTorch cuBLAS. 

__global__ void gemv_bf16_kernel(
    const __nv_bfloat16* __restrict__ x,    // Input activation [M, K]
    const __nv_bfloat16* __restrict__ W,    // Weight matrix [N, K]
    __nv_bfloat16* __restrict__ y,          // Output vector [M, N]
    int M, int N, int K
) {
    // 1. Map thread blocks to Output dimensions (row = m, col = n)
    int n = blockIdx.x;  // Each block handles one output neuron (col)
    int m = blockIdx.y;  // Each block handles one token (row)
    if (n >= N || m >= M) return;

    // 2. Cast pointers to 2-element bfloat16 pairs (SIMD2)
    const __nv_bfloat162* x2 = reinterpret_cast<const __nv_bfloat162*>(x + m * K);
    const __nv_bfloat162* w2 = reinterpret_cast<const __nv_bfloat162*>(W + n * K);
    int num_pairs = K / 2;

    float acc = 0.0f;
    int tid = threadIdx.x;
    int stride = blockDim.x * 4; // Each thread processes 4 pairs (8 elements) per step

    // 3. Main Loop: 128-bit Vectorized Memory Streaming
    for (int i = tid * 4; i < num_pairs; i += stride) {
        if (i + 3 < num_pairs) {
            // 128-bit load: fetches 16 bytes (8 bfloat16 numbers) in ONE transaction
            float4 x_raw = *reinterpret_cast<const float4*>(&x2[i]);
            float4 w_raw = *reinterpret_cast<const float4*>(&w2[i]);
            
            const __nv_bfloat162* x_vec = reinterpret_cast<const __nv_bfloat162*>(&x_raw);
            const __nv_bfloat162* w_vec = reinterpret_cast<const __nv_bfloat162*>(&w_raw);
            
            // Unrolled dot product in high-precision float32 registers
            #pragma unroll
            for (int j = 0; j < 4; ++j) {
                acc += __bfloat162float(x_vec[j].x) * __bfloat162float(w_vec[j].x)
                     + __bfloat162float(x_vec[j].y) * __bfloat162float(w_vec[j].y);
            }
        }
    }

    // 4. Intra-Warp Reduction Tree: 32 threads collapse into 1 value via Shuffles
    #pragma unroll
    for (int mask = 16; mask > 0; mask /= 2) {
        acc += __shfl_down_sync(0xffffffff, acc, mask);
    }

    // 5. Inter-Warp Reduction: 8 warp leaders store into Shared Memory
    __shared__ float warp_sums[8];
    int warp_id = tid / 32;
    int lane_id = tid % 32;
    if (lane_id == 0) warp_sums[warp_id] = acc;
    __syncthreads();

    // 6. Final reduction by Warp 0 and write back to DRAM
    if (warp_id == 0) {
        float val = (lane_id < 8) ? warp_sums[lane_id] : 0.0f;
        #pragma unroll
        for (int mask = 4; mask > 0; mask /= 2) {
            val += __shfl_down_sync(0xffffffff, val, mask);
        }
        if (lane_id == 0) y[m * N + n] = __float2bfloat16(val);
    }
}
Why this beats cuBLAS by 2.33×: For single token decode (M = 1), cuBLAS sets up a general-purpose GEMM grid that incurs 5 to 8 μs of launch overhead. Our custom kernel uses exactly the right grid size (1 block per neuron), streams weights at peak HBM bandwidth, and collapses values in registers in 4.4 μs total.

3.2 In-Place Fused RMSNorm & Gate Kernel (muse_attention_decode)

Computes the Attention Output normalization and applies the elementwise Sigmoid/Identity gate in a single pass:

Mathematical Formulation y = RMSNorm(x, w) × gate [ x / √( (1/D) ∑ xi2 + ε ) × w ] × gate 
__global__ void fast_norm_gate_kernel(
    __nv_bfloat16* __restrict__ o,          // [B, D] input and in-place output
    const __nv_bfloat16* __restrict__ gate, // [B, D] gate vector
    const __nv_bfloat16* __restrict__ w,    // [D] RMSNorm weights
    int B, int D, float eps
) {
    int b = blockIdx.x;  // 1 block per batch token
    int tid = threadIdx.x;
    if (b >= B) return;

    __nv_bfloat16* o_row = o + b * D;
    const __nv_bfloat16* gate_row = gate + b * D;

    // 1. Calculate sum of squares across dimension D
    float sum_sq = 0.0f;
    for (int i = tid; i < D; i += blockDim.x) {
        float val = __bfloat162float(o_row[i]);
        sum_sq += val * val;
    }

    // 2. Warp-level sum reduction
    #pragma unroll
    for (int mask = 16; mask > 0; mask /= 2) {
        sum_sq += __shfl_down_sync(0xffffffff, sum_sq, mask);
    }

    // 3. Block-level sum via Shared Memory
    __shared__ float shared_sums[16];
    int warp_id = tid / 32;
    int lane_id = tid % 32;
    if (lane_id == 0) shared_sums[warp_id] = sum_sq;
    __syncthreads();

    // 4. Compute reciprocal root mean square (RMS)
    __shared__ float r_rms;
    if (tid == 0) {
        float total_sum = 0.0f;
        for (int i = 0; i < (blockDim.x / 32); ++i) total_sum += shared_sums[i];
        r_rms = rsqrtf(total_sum / static_cast<float>(D) + eps);
    }
    __syncthreads();

    // 5. In-Place Fused Update: Norm + Weight Scale + Gate Multiplier
    float inv_rms = r_rms;
    for (int i = tid; i < D; i += blockDim.x) {
        float val = __bfloat162float(o_row[i]) * inv_rms * __bfloat162float(w[i]);
        float g = __bfloat162float(gate_row[i]);
        o_row[i] = __float2bfloat16(val * g); // Written directly back to DRAM once!
    }
}

3.3 Marlin MoE Block Size Auto-Tuning (muse_moe_w4a16)

Marlin is the state-of-the-art GEMM runner for 4-bit weights on Hopper. In SGLang, Marlin groups tokens into chunks of size block_size_m.

The Hidden Padding Bottleneck
In stock SGLang, the formula forced block_size_m = 48 for 128 tokens and block_size_m = 64 for 256 tokens.
Because tokens are routed across 8 sparse experts, each expert received an average of only 128 / 8 = 16 tokens!
SGLang was padding every expert with 32 to 48 empty dummy tokens, wasting massive computation.

Our Fix: We overrode Marlin's heuristic to force block_size_m = 32. This eliminated unnecessary padding across all expert tiles, dropping Verify 32 latency by 152 μs and boosting MoE speed to 1.256× (Rank #1296).

3.4 Asynchronous CUDA Streams (muse_decode_layer)

In the full transformer layer, Attention and MoE Routing are independent until the attention output is required. We used dual asynchronous CUDA streams: 

# Stream 0: Primary compute stream
# Stream 1: Background router stream
stream_router = torch.cuda.Stream()

with torch.cuda.stream(stream_router):
    # Compute Router GEMV asynchronously in the background
    router_logits = fast_gemv_router(normed_x, hi_w, lo_w)

# Meanwhile on primary stream: run FlashAttention-3
attn_out = flash_attn_func(q, k, v)

# Synchronize streams: wait only when router logits are needed
torch.cuda.current_stream().wait_stream(stream_router)

This completely hides the 4.4 μs router computation behind the attention kernel!

Chapter 4: The Serving Track & SGLang Architecture

4.1 How SGLang Works Under the Hood

SGLang (Structured Generation Language) is designed for ultra-high throughput LLM serving. Its architecture consists of:

  1. Tokenizer / HTTP Manager: Accepts incoming client requests and queues prompt tokens.
  2. RadixAttention / Cache Engine: Manages KV cache memory in paged blocks (Radix trees) so prompts sharing a common prefix reuse cached KV tensors.
  3. Central Scheduler (managers/scheduler.py): Forms continuous batches of tokens (combining new prompts and ongoing decode streams).
  4. Model Runner (model_executor/model_runner.py): Executes the model forward pass using CUDA Graphs to eliminate Python CPU launch overhead.

4.2 What is DFlash Speculative Decoding?

Speculative decoding is the core technology evaluated in the Serving Track. Generating 1 token at a time is slow because memory bandwidth throttles the GPU.

  • Step 1 (Drafting): A small, ultra-fast draft model (RadixArk/Muse-Spark-Open-DFlash2) quickly guesses 8 future tokens.
  • Step 2 (Verification): The giant 816B Muse model on our 8×H200 cluster executes a single forward pass with Batch size M = 8 tokens to verify all 8 guesses in parallel!
  • Step 3 (Acceptance): If the draft matches, the server emits 8 tokens in the time of 1.

Chapter 5: What We Are Building Next & How We Will Test It

5.1 The Holy Grail: Tiled Shared-Memory GEMV for M = 8

During the sprint, our naive M = 8 kernel caused a slowdown because it streamed the 67.1 MB weight matrix 8 separate times, thrashing the 50 MB L2 cache.

Over the next 5 days, we are building a Tiled Shared-Memory Kernel:

  1. A thread block loads a 64 × 64 tile of weights from DRAM into Shared Memory once.
  2. All 8 draft tokens are held in registers.
  3. Tensor math executes against the shared weights across all 8 tokens simultaneously.
  4. Result: DRAM traffic drops from 8 × 67.1 MB = 536 MB down to exactly 67.1 MB. The L2 cache is protected, unlocking massive speedup for DFlash verification!
